# Multi-Agent Quality Evaluation — Scenario Table

Source: [multi_agent_quality_eval.py](multi_agent_quality_eval.py) · Full report: [MULTI_AGENT_QUALITY_EVAL_REPORT.md](MULTI_AGENT_QUALITY_EVAL_REPORT.md)

| Scenario | Description | What it Uniquely Tests | How It's Evaluated | Result |
|---|---|---|---|---|
| **1. Hidden Fact Retrieval** | A random project code (e.g. `PHOENIX-4F2A17`) is seeded into an agent's private memory **before** the team is built. The team is then asked to state that code. | The atomic "can MemHub recall one specific datum" path. No collaboration, no summarisation, no ACL edge cases — a FAIL here localises the bug to **retrieval + context injection** and invalidates every downstream scenario. | Substring match `project_code in final_reply` on the last message of the `group_chat`. Metric: `recall_accuracy ∈ {0.0, 1.0}`. | **PASS expected** — proves the `MemHubInterceptor` pre-call hook correctly hits `/v1/retrieve`, ranks the seeded row above noise, and injects it into the system prompt. |
| **2. Cross-Agent Handover** | Researcher writes "Glow-in-the-dark Mushrooms" to the `shared` namespace; the Analyst (a different agent id) must recover it. | The only scenario crossing an agent-id boundary, exercising ACL and the `include_shared=True` retrieval path. | Last Analyst message must contain the ingredient (case-insensitive); `collaboration_score ∈ {0,1}`. | **PASS**, backed by [multi_agent_shared_collab.json](results/memhub/multi_agent_shared_collab.json) — 16 cross-agent reads, ~21% faster p50 retrieve vs baseline. |
| **3. Policy Pressure (Demotion)** | Fifteen verbose observations are written, then the key fact ("deployment date is October 24th") is appended last, so the PolicyEngine compresses the oldest 70% before the task runs. | The only scenario that triggers live LLM summarisation during seeding — verifies the newest-30% carve-out keeps the key fact and the summariser doesn't hallucinate. | Substring match `"October 24th" in final_reply`; `robustness_score ∈ {0,1}`. | **PASS expected** — validates the 70/30 split and the 1 500-token interceptor ceiling guard. |
| **4. Namespace Isolation** | One agent writes a `private` password and a `shared` API key; a different agent is asked to return the key without leaking the password. | The only negative-path/security test — fails if MemHub is too permissive, the usual failure mode of memory systems. | Compound predicate `(API key in reply) AND (password NOT in reply)`; `security_score ∈ {0,1}`. | **PASS expected** — validates ACL filters at both tiers; any FAIL here is a release blocker. |
| **5. Conflict Resolution** | The same agent writes two contradictory status records 1 s apart: `"PENDING"` then `"APPROVED (Updated 1 minute ago)"`. Team is asked for the "current status based on the most recent memory". | The only scenario whose correctness depends on the **recency-decay term** in the hybrid-ranker formula `keyword_hits + recency_decay + log(access_count)` in [core/retrieval.py](../core/retrieval.py). A naive pure-keyword ranker would surface both records with equal weight. | Compound predicate: `("APPROVED" in reply) AND ("PENDING" NOT in reply)`. Metric: `recency_score ∈ {0.0, 1.0}`. | **PASS expected** — proves the recency-decay weight is tuned strongly enough to push a one-second-newer record above its older twin in the merged top-k. Justifies the recency term's existence. |
